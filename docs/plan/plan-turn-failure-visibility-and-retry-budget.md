# Plan: 失敗した Turn の可視化と LLM 待ち時間の上限

## 背景

本番ログの調査で2件の実害が見つかった。

**失敗がユーザーに届かない。** Turn の失敗は内部状態にしか残らず、Web UI が読む履歴には何も入らない。リロードで消え、接続が切れていればそもそも表示されない。本番では「いまいる？」への応答が 429 で失敗したが、返信もエラー通知も履歴に存在せず、ユーザーからは無反応に見えていた。

**LLM の待ち時間に上限がない。** 接続後に何も返らない状態を 300 秒待ち、それが3回分続くため、飽和した上流が Turn を最大15分止められる。制限していたのは試行の開始時点だけで、開始したリクエスト自体は縛られていなかった。

## 方針

### 失敗の可視化

- 失敗を会話のエントリとして永続化する。履歴を唯一の情報源とする UI では、履歴に無いものは存在しないのと同じ
- 状態遷移と会話エントリは同一 transaction で確定する。分けると「Turn は端末なのに履歴が無い」状態が残り、起動時 recovery も端末 Turn を対象にしないため補完されない
- 内部診断と会話に出す文言を分ける。fingerprint 不一致や payload 解読失敗の詳細は運用者向けであり、利用者が読む文ではない
- `uncertain` は出力や Tool 副作用が既に発生している可能性があるため、再送を促さず結果の確認を促す。起動時 recovery と同じ判断基準に揃える
- 会話エントリの文言を push チャネルにもそのまま使う。2箇所で組み立てると、片方だけが再実行を促す状態になり得る
- 失敗エントリは LLM の文脈から除外する。エージェントが自分のエラーを会話として読む理由はない

### 待ち時間の上限

- 1 回の model iteration に総量の期限を設け、各試行は残り時間で打ち切る。試行の開始だけを制限しても上限にならない
- 1 回目の試行は期限の全量を使えるようにする。正常に進行する長い生成を巻き込まないため
- 無応答の期限を別に設ける。read のたびにリセットされるので、進行中の生成は落とさず、接続後に何も返らない状態だけを早く検出できる
- 試行回数の記録とバックオフ待機も期限の内側に入れる。provider から見えない処理であり、外に置くと DB 待ちが長い場合に上限を超える
- 指数バックオフに jitter を掛ける。複数の会話が同時に同じレート制限へ当たったとき、固定 delay では同時にリトライする。`Retry-After` があればサーバーの指示を優先する

## 検証

```
cargo fmt --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test
npm run typecheck --prefix web
npm test --prefix web
```

テストで担保する振る舞い:

| 対象 | 内容 |
|---|---|
| 失敗エントリ | 状態遷移と同じ transaction で作られる／同じ Turn から重複しない／起動時 recovery と dispatcher の破棄でも作られる |
| 文言 | 内部診断が会話に出ない／`uncertain` が再実行を促さない／push 通知が会話と同じ文言になる |
| LLM 文脈 | 通常会話と Pulse のどちらも失敗エントリを読まない |
| 期限 | 試行・待機・リトライ前処理がすべて期限で打ち切られる／バックオフが期限を跨ぐ場合はリトライしない |
| Web | 失敗エントリがエラー項目として描画される |

文言と期限のテストは、修正を戻すと失敗することを確認している。
