# よいコードを書くための確認観点

## 基本方針

よいコードとは、単に正しく動くコードではなく、**目的と概念が妥当で、境界と依存が健全であり、実行時に信頼でき、長期的な変更と運用に耐えるコード**である。

本観点は、ISO/IEC 25010、SOLID、GRASP、Clean Architecture、CUPID、Twelve-Factor App、一般的なコードレビュー観点を踏まえ、日常の設計・実装・レビューで使いやすいように4分類へ整理したものである。

## 確認観点マトリクス

| 大分類              | 中心となる問い                  | 確認観点                                                                                                                                 |
| ---------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| **1. 目的・概念の妥当性** | 正しい問題を、正しい概念で扱っているか      | **目的適合**：実装が満たすべき価値・要件・スコープが妥当か<br>**概念整合**：ドメイン上の概念・状態・関係性が自然に表現されているか<br>**制約保護**：守るべきルール・不変条件・禁止状態がコード上で強制されているか                  |
| **2. 境界・依存の健全性** | 責務の分け方と依存方向は健全か          | **責務境界**：同じ理由で変わるものがまとまり、違う理由で変わるものが分かれているか<br>**依存方向**：中核ロジックが外部都合・技術詳細・具象実装に引きずられていないか<br>**変化点分離**：変更されやすい部分が局所化され、不要な影響波及を起こさないか |
| **3. 実行時の信頼性**   | 実際に動いたとき、期待通りかつ安全に振る舞うか  | **契約充足**：入力・出力・状態変化が期待される契約を満たしているか<br>**失敗制御**：異常系・境界条件・外部失敗に対して、壊れ方が制御されているか<br>**堅牢性**：セキュリティ・性能・並行性・リソース使用が、現実的な負荷や悪条件に耐えるか     |
| **4. 変更・運用の持続性** | 時間が経っても、直せる・調査できる・引き継げるか | **検証可能性**：変更後に正しさを確認でき、回帰を検知できるか<br>**観測可能性**：本番で起きた事象を、ログ・メトリクス・トレース等から追跡できるか<br>**継承可能性**：設定・移行・設計判断・運用手順が、未来の変更者に引き継げる形になっているか    |

## 各分類の説明

### 1. 目的・概念の妥当性

コードが解いている問題そのものが妥当かを見る分類である。

**目的適合**：「このコードは何のために存在するか」を見る。要件に合っているか、スコープが広すぎないか、必要な振る舞いが抜けていないかを確認する。

**概念整合**：「その問題をどういう概念として切り取っているか」を見る。ドメイン上の用語・状態・関係性・ライフサイクルが、コード上の型・モデル・関数・モジュールに自然に対応しているかを確認する。

**制約保護**：「破ってはいけないルールが強制される形になっているか」を見る。不変条件・禁止状態・業務ルール・入力制約が、型・バリデーション・DB制約・テストなどで保護されているかを確認する。

この分類で重要なのは、処理が動くかよりも**問題の捉え方が正しいか**である。

---

### 2. 境界・依存の健全性

コードの置き場所・責務の分け方・依存方向が健全かを見る分類である。

**責務境界**：「何を同じ単位として扱うべきか」を見る。同じ理由で変わるものが近くにあり、違う理由で変わるものが分かれているかを確認する。

**依存方向**：「何が何を知ってよいか」を見る。ドメインやユースケースなどの中核ロジックが、DB・UI・外部API・フレームワークなどの技術詳細に引きずられていないかを確認する。

**変化点分離**：「変更されやすい部分が局所化されているか」を見る。Provider差し替え・DB変更・API変更・仕様追加などが、自然な範囲に閉じるかを確認する。

この分類で重要なのは、コードを綺麗に分けることではなく**変更理由に沿って分けること**である。

---

### 3. 実行時の信頼性

コードが実際に動いたとき、期待通りかつ安全に振る舞うかを見る分類である。

**契約充足**：「正常に使われたとき、期待される入出力と状態変化を満たすか」を見る。関数・API・ユースケース・ジョブなどが、呼び出し側との契約を満たしているかを確認する。

**失敗制御**：「想定外や悪条件のとき、壊れ方が制御されているか」を見る。不正入力・null・0件・重複・外部API失敗・DBエラー・タイムアウト・リトライ・ロールバックなどを確認する。

**堅牢性**：「現実の負荷や悪条件に耐えられるか」を見る。セキュリティ・性能・並行性・リソース使用・権限・秘密情報の扱いなどを確認する。

この分類で重要なのは、失敗を完全になくすことではなく**失敗しても被害が限定され、状態が破壊されないこと**である。

---

### 4. 変更・運用の持続性

コードが時間の経過に耐えられるかを見る分類である。

**検証可能性**：「変更後に正しさを確認できるか」を見る。単体テスト・結合テスト・E2Eテスト・型チェック・lint・CIなどによって、変更の安全性を確認できるかを見る。

**観測可能性**：「本番で何が起きたかを追えるか」を見る。ログ・メトリクス・トレース・エラー情報・処理ID・リクエストIDなどから、実行時の状態や障害原因を追跡できるかを見る。

**継承可能性**：「未来の変更者が引き継げるか」を見る。設定・環境差分・移行手順・設計判断・制約・運用手順・ドキュメントが、暗黙知に閉じず残されているかを見る。

この分類で重要なのは、今の実装を完成させることではなく**未来の変更・調査・移行を可能にしておくこと**である。

---

## 表現品質の扱い

命名、コメント、可読性、一貫性は独立した大分類にはしない。これらは、各分類を支える補助観点として扱う。

- 名前がドメイン概念とズレているなら、**目的・概念の妥当性**の問題である
- 責務が名前から分からないなら、**境界・依存の健全性**の問題である
- 条件分岐が複雑で異常系を追えないなら、**実行時の信頼性**の問題である
- 判断理由が残っていないなら、**変更・運用の持続性**の問題である

表現が綺麗であること自体を評価するのではなく、意味・境界・振る舞い・持続性を正しく支えているかを見る。

## まとめ

よいコードは、次の4分類で確認する。

| 大分類           | 確認すること                   |
| ------------- | ------------------------ |
| **目的・概念の妥当性** | 正しい問題を、正しい概念で扱っているか      |
| **境界・依存の健全性** | 責務の分け方と依存方向は健全か          |
| **実行時の信頼性**   | 実際に動いたとき、期待通りかつ安全に振る舞うか  |
| **変更・運用の持続性** | 時間が経っても、直せる・調査できる・引き継げるか |

この4分類は、コードを表面的な綺麗さではなく、長期運用に耐える設計資産として評価するための観点である。
